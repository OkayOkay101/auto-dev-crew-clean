# Design: github-docs skill (Library Router)

- วันที่: 2026-11-18
- สถานะ: **ร่าง รอการอนุมัติ** ยังไม่ได้สร้างสกิล ยังไม่ได้ commit
- ที่มา: [STATE-github-docs-skill.md](../../../STATE-github-docs-skill.md) และผลค้นหาสกิลภายนอกในแชทนี้

## 1. เจตนาและเหตุผล (Intent)

เมื่อผู้ใช้สั่งใน Claude Code ว่า "เขียนเอกสาร" ให้ repo หนึ่ง เอเจนต์มักเขียนจากความจำหรือเดา ทำให้ลิงก์พัง คำสั่งไม่ตรงกับโค้ด และ README ภาษาไทยกับอังกฤษไม่ตรงกัน สกิล `github-docs` ต้องทำให้ทุกข้อความในเอกสารมีที่มาในโค้ด ตรวจได้ด้วยสคริปต์ และส่งต่อเป็น PR โดยผู้ใช้อนุมัติก่อนทุกขั้นที่ส่งผลออกนอกเครื่อง

## 2. เป้าหมาย (Goals)

1. สร้างหรือปรับ README, คู่มือผู้ใช้, About text, และ release notes ของ repo ได้
2. เขียนคู่ภาษาไทยและอังกฤษ โดยให้โครงสร้างและลิงก์ตรงกัน
3. ทุก claim เชิงข้อเท็จจริง (คำสั่ง, path, พอร์ต, ชื่อฟังก์ชัน, ค่าเริ่มต้น) ต้องชี้ไปยังไฟล์และบรรทัดในโค้ดได้
4. ตรวจลิงก์เสียและความยาว release notes ด้วยสคริปต์
5. ผ่านกระบวนการ outline → อนุมัติ → เขียน → ตรวจ → รายงาน → PR

## 3. ไม่ทำ (Non-goals)

- ไม่สร้าง Diátaxis scaffolding ทั้งสี่โฟลเดอร์โดยอัตโนมัติ (ตามที่ Roritharr/diataxis-skill ระบุว่าไม่ควรทำ)
- ไม่แปลเอกสารเป็นภาษาอื่นนอกจากไทยและอังกฤษ
- ไม่ publish release และไม่ merge PR เอง
- ไม่ดาวน์โหลดหรือรันซอฟต์แวร์จาก catalog ตามกฎ Library Router

## 4. ข้อห้าม (Anti-goals)

ถ้าเกิดเหตุการณ์ต่อไปนี้ ถือว่าสกิลล้มเหลวแม้ไฟล์จะถูก:

- เขียนคำสั่งหรือ path ที่รันไม่ได้โดยไม่มีการตรวจกับโค้ด
- แก้ไฟล์ release asset หรือ merge PR โดยไม่ได้รับคำสั่งจากผู้ใช้
- เขียนทับ `CHANGELOG.md` หรือเอกสารเดิมโดยไม่แจ้ง
- ใส่ลิงก์ PR ที่สืบย้อนไม่ได้ว่าเป็นของ commit นั้นจริง

## 5. ข้อจำกัด (Constraints)

- Library Router: สถานะ `checked` หมายถึงผ่านการตรวจแบบ static เท่านั้น ไม่ใช่ผ่านการทดสอบการใช้งานจริง
- ใช้ไลเซนส์ที่ยืนยันแล้วเท่านั้น ห้ามคัดลอกโค้ดหรือเนื้อหาจาก doc-drift-detector (MIT + Commons Clause) และ travcunn/diataxis-skill (CC BY-SA 4.0) ให้อ้างอิงแนวคิดแล้วเขียนเอง
- สคริปต์ตรวจต้องใช้ Python standard library อย่างเดียว เพื่อไม่ต้องติดตั้งเพิ่ม
- ไม่ commit หรือ push จนกว่าผู้ใช้จะสั่ง
- ไม่ใส่ path ส่วนตัวของผู้ใช้ลงในผลลัพธ์ที่จะ publish

## 6. แนวทางที่พิจารณา (Approaches)

| แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| **A. สกิลกว้างหนึ่งตัว + ไฟล์ reference ต่อประเภทเอกสาร** | ใช้ง่าย มี workflow เดียว แชร์สคริปต์ตรวจร่วมกัน | SKILL.md ต้องกระชับ ต้องแยกเนื้อหาไปไว้ใน references |
| B. ตระกูลสกิลแยกตามประเภท (readme-, release-, about-) | แต่ละตัวเล็ก | ผู้ใช้ต้องเลือกเอง และตรวจซ้ำในหลายที่ |
| C. ห่อสกิลภายนอกตัวเดียว (เช่น awesome-copilot) | ติดตั้งไวที่สุด | ไม่มีการตรวจ claim และไม่มี PR flow ซึ่งเป็นเป้าหมายหลัก |

**ที่เลือก: A** เพราะตรงกับการตัดสินใจที่บันทึกไว้ใน STATE เดิม และเป็นทางเดียวที่รวมการตรวจกับ PR flow ไว้ในที่เดียว ผู้ใช้ยังไม่ได้ยืนยันการเลือกนี้ในแชท จึงถือเป็น **ข้อเสนอของผม** ที่ต้องรับการอนุมัติ

## 7. การออกแบบ (Design)

### 7.1 โครงสร้างไฟล์

```
github-docs/
├── SKILL.md                      # workflow หลัก กระชับ
├── references/
│   ├── readme.md                 # โครง README (ผู้ใช้/นักพัฒนา)
│   ├── user-guide.md             # คู่มือผู้ใช้ตามภาพหน้าจอและขั้นตอน
│   ├── release-notes.md          # เทมเพลต, Breaking Changes, การอ้าง PR
│   ├── about-text.md             # About + topics ของ repo
│   └── diataxis.md               # ใช้เมื่อผู้ใช้ขอโครงแบบ Diátaxis
└── scripts/
    ├── check_links.py            # ลิงก์ภายในและ anchor ที่เสีย
    ├── check_claims.py           # claim → file:line ที่รองรับ
    ├── check_release_notes.py    # ความยาว (< 2000 ตัวอักษร) และหมวดหัวข้อ
    └── check_bilingual.py        # โครงหัวข้อและลิงก์ของคู่ไฟล์ EN/TH ตรงกัน
```

`check_bilingual.py` เป็นข้อเสนอของผมที่ไม่ได้อยู่ในแผนเดิม (ดูข้อ 10)

### 7.2 Workflow

1. **ระบุประเภทและผู้อ่าน** (Diátaxis ข้อแรก): ถามผู้ใช้เฉพาะเมื่อไม่ชัด เช่น README เพื่อใคร และต้องการภาษาไหน
2. **สำรวจโค้ด** อ่านจุดเข้าใช้งาน, ไฟล์ config, สคริปต์ build, และ test ที่เกี่ยวข้อง ก่อนเขียนอะไรทั้งสิ้น
3. **เสนอ outline แล้วรออนุมัติ** (จาก awesome-copilot) ไม่เขียนเนื้อหาเต็มก่อนผู้ใช้ตอบ
4. **เขียนคู่ภาษา** เช่น `README.md` กับ `README_TH.md` โดยหัวข้อและลิงก์ต้องเท่ากัน
5. **ตรวจ** รันสคริปต์ทั้งสี่ตัว ทุกตัวต้องออก exit 0 หรือรายงานข้อที่ต้องแก้
6. **รายงาน** แสดงผลตรวจ สิ่งที่ไม่ได้ตรวจ และ claim ที่ยังไม่มีที่มา
7. **PR** สร้างเฉพาะเมื่อผู้ใช้สั่ง ไม่ merge เอง
8. **Release** ไม่แทนที่ asset จนกว่าจะผ่านการ build check และได้รับคำสั่ง

### 7.3 การตรวจ claim (หัวใจของสกิล)

- ดึง claim จากเอกสารที่ร่าง เช่น คำสั่ง `python ...`, ชื่อไฟล์, พอร์ต, ค่า default
- ค้นหาในโค้ดแล้วบันทึกคู่ `claim → path:line`
- claim ที่หาไม่เจอ ให้ตกไปที่รายการ "ยังไม่มีที่มา" และบังคับให้ผู้ใช้ตัดสินใจ ไม่ปล่อยผ่านเงียบ ๆ
- ใส่ลิงก์ PR ใน release notes เฉพาะเมื่อ bullet นั้นสืบย้อนไปถึง merge commit ได้ (จาก paperclip)

### 7.4 Release notes

- อ่าน PR title ก่อน commit message เมื่อโปรเจกต์ใช้ PR (จาก kangminhyuk)
- มีหมวด Breaking Changes เสมอ แม้จะว่าง (จาก wshobson)
- วางผลลงในแชทเป็น Markdown พร้อมคัดลอก ไม่เขียนทับ `CHANGELOG.md` (จาก ycs77)
- เขียนไฟล์เฉพาะเมื่อผู้ใช้ขอ และไม่ทับไฟล์เดิมโดยไม่ถาม

## 8. ฟิวชั่นกับแหล่งภายนอก

| สิ่งที่นำมา | จากไหน | ปรับเป็นอย่างไร |
|---|---|---|
| ระบุประเภทเอกสารก่อนเขียน | Diátaxis ใน awesome-copilot และ Roritharr | เป็นขั้นที่ 1 |
| หยุดรอ outline | awesome-copilot | ตรงกับเกตอนุมัติของเรา |
| ตรวจลิงก์ และ claim กับโค้ด | doc-drift-detector | เขียนเองโดยไม่คัดลอกโค้ด |
| ไม่เขียนทับ ไม่ publish เอง | paperclip release-changelog | เป็นกฎ |
| ลิงก์ PR เฉพาะที่สืบได้ | paperclip | เป็นกฎตรวจ |
| หมวด Breaking Changes | wshobson | อยู่ในเทมเพลต |
| ใช้ PR title | kangminhyuk | อยู่ในขั้นสรุป release |
| คู่ไฟล์ README_TH.md | multi-lang-readme และ readme-bilingual-sync | ตั้งชื่อตามนี้ และเพิ่มการตรวจ parity |

## 9. การทดสอบ

- สคริปต์แต่ละตัวมี unit test ด้วย `unittest` พร้อม fixture ของ repo ปลอม ทั้งกรณีผ่านและกรณีเสีย
- ทดลองรันบน `C:\Users\Smart\Documents\DATAelectricWORKs` (โหมด dry run ไม่เขียนไฟล์) เพื่อดูว่าตรวจจับของจริงได้
- สถานะจะเป็น "ผ่านการตรวจแบบ static" จนกว่าจะรันเอเจนต์จริงกับงานเขียนเอกสารหนึ่งชิ้น ซึ่งยังไม่ได้ทำ

## 10. ข้อตัดสินใจที่ผมตัดสินเอง (ตรวจได้)

1. ชื่อไฟล์ไทยเป็น `README_TH.md` (ตามที่ repo DATAelectricWORKs ใช้จริง ปรับตามคำสั่งผู้ใช้ 2026-11-18)
2. เพิ่ม `check_bilingual.py` เพราะคู่ภาษาเป็นข้อกำหนดหลักแต่แผนเดิมไม่มีการตรวจนี้
3. สกิลไม่เรียกเว็บเอง ใช้เฉพาะโค้ดใน repo และไฟล์ที่ผู้ใช้ชี้มา
4. ใช้ Diátaxis เป็นแนวคิด ไม่คัดลอกเนื้อหาจาก travcunn (CC BY-SA)

## 11. ข้อที่ต้องให้ผู้ใช้ตัดสิน

1. **ที่อยู่ของสกิล**: โฟลเดอร์ local ที่สคริปต์ sync อ่าน (เช่น `~/.claude/skills`) หรือ catalog checkout ที่ `C:\Users\Smart\Documents\ChatGPT\test`
2. **แนวทาง**: เห็นด้วยกับแนวทาง A หรือไม่ (ข้อ 6)
3. **ขอบเขต release**: รวม release notes และ About text ในรอบแรก หรือแยกเป็นรอบหลัง
4. **การอนุมัติทีละขั้น**: ต้องการเกต outline ทุกครั้ง หรือเฉพาะงานที่ใหญ่

## 12. สิ่งที่ยังไม่ได้ทำ

- ยังไม่ได้ builder check ด้วย subagent ตามกระบวนการ brainstorming ผู้เขียนอ่านเอกสารนี้เองแล้ว และสรุปเป็นข้อตัดสินใจในข้อ 10 และ 11
- ยังไม่ได้ commit ไฟล์นี้
- ยังไม่ได้ตรวจ license และสถานะการดูแลของ Roritharr/diataxis-skill และ multi-lang-readme
