# ดราฟต์: ปรับระบบเพิ่มโมเดล (BYOP / Pollinations) ให้ลื่นขึ้น

สถานะ: **ลงมือทำแล้ว (ยังไม่ commit)** ดูผลและการตัดสินใจที่เลือกในหัวข้อ 5 ด้านล่าง

## 1. สิ่งที่พบจากโค้ดปัจจุบัน

| ประเด็น | หลักฐาน | ผลกระทบ |
|---|---|---|
| มี UI โมเดล 2 ชุดซ้อนกัน | `static/index.html` บรรทัด ~555-587 (ช่องพิมพ์ `byopModelId` + checkbox role) กับ `static/index_sidebar.html` บรรทัด ~913-921 (ส่วน `byopModelSection` + ปุ่ม "ดึงโมเดลจาก API") | ไม่ชัดว่าชุดไหนถูกใช้จริง ต้องยืนยันว่า `gui.py` เสิร์ฟไฟล์ไหน |
| ช่องเพิ่มโมเดลเป็นข้อความอิสระ | `byop_store.add_model` ตรวจแค่ regex `pollinations/...` | พิมพ์ชื่อผิดแล้วบันทึกได้ ไม่ตรวจกับแคตตาล็อก Pollinations |
| มีตัวดึงแคตตาล็อกอยู่แล้วแต่ไม่ได้ใช้กับ BYOP | `keys.fetch_provider_models` และ `/api/models` (gui.py ~1053) | ทำ dropdown จากรายการจริงได้โดยไม่ต้องเขียน endpoint ใหม่ |
| โมเดลหนึ่งบทบาทหลายตัวได้ เลือกตัวแรกแบบเงียบ ๆ | `byop_store.model_for_role` คืนตัวแรกที่มี role | ผู้ใช้ไม่รู้ว่าโมเดลไหนถูกใช้ |
| ไม่มี edit เฉพาะบทบาท | `byopRenderModels` มีแค่ "ลบ" ข้อความ role ไม่มี pill เหมือนการ์ดคีย์ | ต้องลบแล้วเพิ่มใหม่เพื่อเปลี่ยน role |
| ไม่มีการทดสอบโมเดลก่อนผูก | `add_model` บันทึกทันที | โมเดลที่คีย์ไม่มีสิทธิ์จะล้มตอนรันงานจริง |
| ค่าเริ่มต้นไม่ตรงกันในหลายที่ | `byop.DEFAULT_MODEL = pollinations/openai/gpt-6-luna`, placeholder ใน index.html, `config.yaml` | แก้ที่เดียวไม่พอ ต้องรวมเป็นค่าเดียว |
| ข้อความ error/สถานะกระจัดกระจาย | `byopPoolMsg` และ `byopScanOut` | ผู้ใช้ไม่รู้ว่าเพิ่มสำเร็จหรือไม่ |

สถานะเทสต์: `tests/test_byop_model_picker.py` ผ่าน 3/3 (ตรวจว่าการ์ดในไฟล์ sidebar มีปุ่มดึงโมเดล ไม่ได้ทดสอบว่า UI ทำงานจริง)

มีไฟล์ที่ยังไม่ commit 17 ไฟล์ (ตาม git status) รวมถึง `byop_store.py` ซึ่งเป็นแกนของระบบโมเดลตามบทบาท ควร commit ก่อนเริ่มแก้

## 2. สกิลที่ค้นพบ (Library Router)

- `onboarding` (local, checked): แอนิเมชันขั้นตอนต้อนรับ ไม่เกี่ยวกับการเพิ่มโมเดลโดยตรง ใช้ได้เฉพาะถ้าจะทำ onboarding
- `component-animations`, `ui-micro` (local, checked): สถานะปุ่ม/ฟอร์มและ feedback ตอนบันทึก ใช้ได้เล็กน้อยกับ feedback หลังกดเพิ่มโมเดล
- `domain-modeling` (mattpocock, imported): ช่วยนิยามคำศัพท์ เช่น "โมเดล", "บทบาท", "คีย์" ใน GLOSSARY ไม่ได้แก้ UI
- `prototype` (mattpocock, imported): สร้างต้นแบบทิ้งเพื่อลองหน้าตา UI ก่อนลงโค้ดจริง เหมาะกับการเลือกแบบ dropdown เทียบกับช่องพิมพ์

ไม่พบสกิลที่ตรงกับ "เพิ่มโมเดลผู้ให้บริการ" โดยตรง (ค้นสองรอบด้วยคำว่า model registry, model picker, provider configuration, dropdown validation) จึงยังไม่ได้โหลดสกิลใดมาใช้ ไม่ได้ติดตั้งอะไรเพิ่ม

## 3. ข้อเสนอการเปลี่ยนแปลง (เรียงตามลำดับ)

**ขั้น A: รวม UI ให้เหลือชุดเดียว**
- ยืนยันก่อนว่า gui.py เสิร์ฟ `index.html` หรือ `index_sidebar.html`
- เอาชุดที่ไม่ได้ใช้ออก ย้ายการ์ด BYOP ให้อยู่ที่เดียว

**ขั้น B: เปลี่ยนช่องพิมพ์เป็น dropdown จากแคตตาล็อก**
- ใช้ `keys.fetch_provider_models("opencode-pollinations", ...)` หรือ `/api/models` ที่มีอยู่
- ให้ผู้ใช้เลือกจากรายการจริง มี fallback เป็นช่องพิมพ์ เมื่อดึงรายการไม่ได้
- ตรวจว่า ID ที่เลือกอยู่ในแคตตาล็อก ก่อนบันทึก

**ขั้น C: แก้บทบาทได้ในที่เดียว**
- แสดง role เป็น pill แบบเดียวกับการ์ดคีย์ กดเพื่อสลับได้
- ทำให้บทบาทหนึ่งมีโมเดลเดียว (เพิ่มโมเดลใหม่ที่ role ซ้ำ = ย้ายบทบาทมาให้โมเดลใหม่ แสดงข้อความยืนยัน)
- ผลนี้สอดคล้องกับ `model_for_role` ที่คืนตัวเดียวอยู่แล้ว

**ขั้น D: ทดสอบโมเดลก่อนผูก (ทางเลือก)**
- เรียก endpoint เล็ก ๆ ด้วยคีย์ที่เลือกเพื่อดูว่าโมเดลใช้ได้ ค่าใช้จ่ายและ quota ต้องพิจารณา

**ขั้น E: รวมค่าเริ่มต้นและ feedback**
- ให้ `DEFAULT_MODEL` เป็นแหล่งเดียว แล้วให้ UI/config อ้างอิงจากนั้น
- ใช้ `byopPoolMsg` เดียวสำหรับสถานะทุกปุ่ม พร้อมข้อความสำเร็จ/ล้มเหลวที่ชัดเจน

**ขั้น F: เทสต์**
- อัปเดต `test_byop_model_picker.py`, `test_byop_routes.py`, `test_byop_role_model.py`
- เพิ่มเทสต์: บทบาทซ้ำย้ายโมเดล, ID นอกแคตตาล็อกถูกปฏิเสธ, dropdown ไม่มีข้อมูลแล้ว fallback
- รัน `python -m pytest -q -p no:cacheprovider` ให้ผ่านทั้งชุด

## 4. สิ่งที่ยังไม่รู้ / ต้องตัดสินใจ

1. ใช้ UI ไฟล์ไหนจริง (`index.html` หรือ `index_sidebar.html`) ต้องตรวจก่อนลงมือ
2. ต้องการให้ดึงแคตตาล็อกจาก API เสมอ หรือให้ใช้รายการที่ cache ไว้ เพื่อลดการเรียกเครือข่าย
3. ขั้น D (ทดสอบโมเดลก่อนผูก) ทำหรือไม่ เพราะจะใช้โควตา Pollen จริง
4. บทบาทหนึ่งมีโมเดลเดียวตามข้อเสนอขั้น C ใช่หรือไม่ หรือยังอยากให้หลายโมเดลต่อบทบาทได้

## 5. ผลการลงมือทำ (ตัดสินใจเองตามค่าเริ่มต้นที่เสนอ)

- **A** ยืนยันแล้วว่า `/` เสิร์ฟ `index_sidebar.html` (UI หลัก) และ `/classic` เสิร์ฟ `index.html` (UI เดิมสำหรับย้อนกลับ) จึงคงการ์ดใน `index.html` ไว้ ไม่ได้ลบ
- **B** ช่องพิมพ์เปลี่ยนเป็น dropdown จาก `POST /api/byop/models/catalog` มีตัวเลือก "พิมพ์เอง" และ fallback เมื่อดึงรายการไม่ได้ เพิ่มโมเดลจะถูกปฏิเสธถ้า ID ไม่อยู่ในรายการ
- **C** บทบาทหนึ่งมีโมเดลเดียว (`byop_store._claim_roles`) การเพิ่มบทบาทที่มีอยู่แล้วจะย้ายให้โมเดลใหม่และแจ้งว่าย้ายจากตัวไหน ชิปบทบาทกดสลับได้ (`/api/byop/models/roles`)
- **D** ปุ่ม 🧪 ทดสอบ เรียกเมื่อผู้ใช้กดเท่านั้น ส่ง 1 โทเคนต่อ 1 ครั้ง (`/api/byop/models/test`)
- **E** ค่าเริ่มต้นส่งมาจาก `byop.DEFAULT_MODEL` ผ่าน API ไม่ฝัง placeholder ใน HTML แล้ว ข้อความสถานะของการ์ดรวมผ่าน `byopSetMsg` ยังเหลือ `config.yaml` ที่มี engine model ของตัวเอง ซึ่งไม่ได้แก้
- **F** เทสต์: `tests/test_byop_model_flow.py` ใหม่ 22 เทสต์, แก้ `test_byop_routes.py` (ฉีด catalog) และ `test_byop_model_picker.py` เพิ่มอีก 1 เทสต์ ชุดเต็ม `pytest` ผ่าน 1326 passed, 6 skipped

หมายเหตุ: `index.html` (classic) ยังเรียก `/api/byop/models/add` ด้วยช่องพิมพ์เดิม ใช้งานได้เมื่อออนไลน์เพราะมีการตรวจแคตตาล็อกฝั่งเซิร์ฟเวอร์ ยังไม่ได้ทดสอบในเบราว์เซอร์จริง
