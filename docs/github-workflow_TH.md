# ขั้นตอนบน GitHub: ป้าย, issue และ PR

เอกสารนี้อธิบายว่าผู้ใช้ทำอะไรบน GitHub และระบบตอบสนองอย่างไร

---

## 1. ป้าย (label) ทั้งหมด

ป้ายถูกสร้างอัตโนมัติเมื่อ repo ถูกตั้งค่า (`runner.py` ประมาณบรรทัด 1446) ถ้ายังไม่มีในรีโปนั้น

| ป้าย | ค่าในไฟล์ | ใครติด | ความหมาย |
|---|---|---|---|
| `ai-task` | `labels.task` | ผู้ใช้ | issue ที่ให้เอเจนต์หยิบไปทำ |
| `ai-pause` | `labels.pause` | ผู้ใช้ | หยุดเอเจนต์ที่ระดับ repo ตราบใดที่มี issue เปิดอยู่ที่ติดป้ายนี้ |
| `ai-working` | `labels.working` | ระบบ | ติดระหว่างที่เอเจนต์กำลังทำ issue นั้น |
| `ai-failed` | `labels.failed` | ระบบ | ทำไม่สำเร็จหรือไม่ผ่านการประเมิน ระบบจะไม่หยิบซ้ำเอง |
| `ai-needs-human` | `labels.needs_human` (ค่าเริ่มต้น `ai-needs-human`) | ระบบ | ต้องให้คนเข้าไปดู ระบบจะไม่หยิบซ้ำ |
| `ai-generated` | `labels.pr` | ระบบ | ติดบน PR ที่เอเจนต์เปิด |
| `ai-report` | (ค่าคงที่) | ระบบ | ป้ายของรายงานประจำวัน |
| `ai-plan` | (ค่าคงที่) | ระบบ | issue เสนอแผนฟีเจอร์ที่รอการอนุมัติ |
| `ai-plan-approved` | (ค่าคงที่) | ผู้ใช้ | ผู้ใช้อนุมัติแผน ระบบจะสร้าง `ai-task` ให้ |

ป้ายที่ระบบใช้ทุกชื่อตั้งได้ใน `labels` ของ `config.yaml` ยกเว้น `ai-plan`, `ai-plan-approved` และ `ai-report` ซึ่งเป็นค่าคงที่ในโค้ด

## 2. วงจรของ issue ที่ผู้ใช้สั่ง

```
ผู้ใช้เปิด issue
     │
     ▼
ติดป้าย ai-task  ──► (ผู้เขียนไม่ตรงกับ owner → ระบบไม่หยิบ)
     │
     ▼
ระบบหยิบงาน → ติด ai-working
     │
     ├── ผ่านด่านทุกขั้น → เปิด PR (ai-generated)
     │         │
     │         └── ตามโหมด merge → merge เอง หรือรอคนตรวจ
     │
     └── ไม่ผ่าน → เอา ai-working ออก, ติด ai-failed, คอมเมนต์เหตุผลใน issue
```

**สิ่งที่ผู้ใช้ควรทำ**
- เขียน issue ให้ชัดว่าต้องการอะไร และทำให้ทดสอบได้ (เช่น บอกคำสั่งเทสต์หรือพฤติกรรมที่ต้องการ)
- ติด `ai-task` เองเท่านั้น ถ้าคนอื่นติด ระบบจะไม่หยิบ
- ถ้าอยากให้ลองใหม่หลังล้มเหลว ให้เอา `ai-failed` ออกเองและถ้ามี `ai-needs-human` ก็เอาออกด้วย

## 3. การหยุดและการทำต่อ

### หยุดฉุกเฉิน
- เปิด issue ใดก็ได้แล้วติด `ai-pause` runner จะไม่เริ่มงานใหม่ในรอบถัดไป
- งานที่กำลังทำอยู่อาจจบรอบนั้นก่อน
- หรือกดหยุดจาก GUI เพื่อยกเลิกงานที่กำลังทำ

### ทำต่อ
- ปิด issue ที่ติด `ai-pause` ระบบจะกลับมาทำงานในรอบถัดไป (เงื่อนไขคือไม่มี issue เปิดที่ติดป้ายนี้)

## 4. แผนฟีเจอร์ (ai-plan)

วงจร:
1. ที่หน้า **สตูดิโอ** ใน GUI กดให้ AI เสนอแผนฟีเจอร์ ระบบสร้าง issue ป้าย `ai-plan`
2. ผู้ใช้อ่านแผนแล้วติด `ai-plan-approved`
3. ระบบสร้าง issue `ai-task` สำหรับแต่ละขั้นของแผน
4. ผลดำเนินต่อไปตามวงจรของ issue ที่ผู้ใช้สั่ง

รายละเอียดการ propose และ approve ผ่าน `/api/feature-gen/propose` และ `/api/feature-gen/approve` (ดู [api.md](api_TH.md))

ระดับ merge ของแผนตั้งได้ตอนสร้าง (ค่า `merge_level` ต่อ repo)

## 5. PR ที่ระบบเปิด

- ชื่อ branch: `ai/issue-<หมายเลข>-<เวลา>` (issue) หรือ `ai/<ตัวละคร>-<เวลา>` (ตัวละคร)
- ป้าย: `ai-generated`
- ชื่อ PR มีไอคอนตามชนิดงาน (จาก `ICONS` ในโค้ด)
- เนื้อหา PR สร้างจาก `pr_body.py` (รายละเอียดของส่วนที่ใส่ในเนื้อหายังไม่ได้ไล่ตรวจทั้งหมด)

ผู้ตรวจควรดู:
- diff ว่าตรงกับ issue หรือไม่
- ผลเทสต์และ CI
- คะแนน judge และ critique (ถ้าคะแนนต่ำ ให้ระวังเป็นพิเศษ)

---

## 6. ข้อควรรู้เรื่องสิทธิ์และ token

- บัญชี GitHub ที่ `gh` ใช้ ต้องมีสิทธิ์เขียน repo เป้าหมาย เพื่อ push branch, เปิด PR, สร้างป้าย และคอมเมนต์
- ระบบไม่ force-push ตามข้อกำหนดในเอกสาร (รายละเอียดข้อจำกัดอยู่ที่ [troubleshooting.md](troubleshooting_TH.md#2-ข้อจำกัดที่ทราบแล้ว))
- ห้ามใส่ token ลงใน issue หรือคอมเมนต์ ระบบจะซ่อนค่าที่รู้จัก (`redact.py`) ก่อนแสดงหรือบันทึก แต่ไม่ได้รับประกันว่าทุกรูปแบบจะถูกจับได้

---

## 7. รายงานประจำวัน

ระบบเขียนรายงานลงใน issue ป้าย `ai-report` (`report()` ใน `runner.py`) การล้มเหลวของ `gh` ตอนเขียนรายงานจะไม่ทำให้ช่องทำงานหยุด (`_report_safely`)
